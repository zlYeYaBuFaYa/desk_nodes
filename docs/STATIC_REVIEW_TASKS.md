## H1 导入失败可以把活库写到一半

复核结论：不成立。

SQLite 文档约定备份期间在目标库上持有写事务。`sqlite3_backup_step` 还没返回 `SQLITE_DONE` 时，`sqlite3_backup_finish` 回滚这个事务。`Microsoft.Data.Sqlite` 10 的 `BackupDatabase` 把 `sqlite3_backup_init` 的结果放在 `using` 里，`sqlite3_backup_step` 失败抛错时仍会释放句柄并调用 `finish`。现有测试 `DestinationWriteLockCausesBackupFailureAndPreservesLiveData` 在目标库被别的连接写锁锁住时调用 `ReplaceFrom`，断言活库原便签还在。

考虑过的做法：

1. 保持现有 online backup。失败路径已经由 SQLite 回滚，测试也锁住了锁冲突。采用这个。
2. 先 `VACUUM INTO` 临时文件，再关闭活连接并替换文件。窗口和仓库都持有这条连接，关闭再打开的失败面比备份事务更大，也偏离技术设计里的 online backup。
3. 在 `ReplaceFrom` 外再包一层 SQL 事务。备份 API 要求目标库当时没有事务，现有测试已经拒绝事务内替换。

不改 `ReplaceFrom`。磁盘写满时回滚本身也可能失败，这是 SQLite 事务的边界，技术设计要求用故障注入验证，不在这次用静态改写去声称解决。

## H2 取消组词后编辑一直处于组词中

复核结论：成立。`Composing` 只在 `TextInput` 里被清掉。Esc 取消候选通常不产生这个事件，防抖和 `Run` 会一直被挡住。失焦提交也会因为 `Composing` 仍为 true 而跳过。候选窗口抢走焦点时仍然不提交，这条保持不变。

考虑过的做法：

1. 在 Esc 和 `WM_IME_ENDCOMPOSITION` 之后用 `DispatcherPriority.Background` 结束组词，再 `Reschedule`。同一轮组词用 epoch 挡住回调误清下一轮。不把按键标成已处理，IME 仍能取消候选。采用这个。
2. 在按键当时同步清掉 `Composing` 并立刻 `Commit`。候选可能还留在文本框里，会把未确认的字写进库。
3. 失焦就当作组词结束并提交。技术设计要求候选窗口的焦点不能当成结构提交。

输入法确认仍走原来的 `TextInput`。完整候选窗口行为仍要在 Windows 上看。
