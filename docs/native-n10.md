## N8 synchronous History assessment

`HistoryPresentation` is `@MainActor`; `reload()` synchronously calls Store settings/current business date and reads every snapshot/note/item in the selected month on the **same serialized SQLite connection** used by editing/rollover/import. `LazyVStack` only defers view creation; it does not make SQLite reads asynchronous. A month bounds dates, **not item count or per-note SQL query count**. Large histories or database contention (5s SQLite busy timeout) can block the main actor and delay input/pointer/timer handling. Retained low-frequency windows, immutable reads and monthly filtering are useful scope decisions, not evidence of responsiveness.

No Mac latency/CPU/memory measurements exist. No performance threshold was specified. N10 therefore records this honest limitation and includes a realistic dense-month responsiveness gate; it introduces no background connection, actor rewrite, caching or speculative optimization project. Optimize only from an observed, reproducible acceptance failure with a separate explicit scope decision.

## N9 complete-state, rollback and native API review

Durable JSON coverage was checked against **every schema table and model field**: note/item identities, optional titles and exact Unicode/NUL text, colors, completion, order, timestamps/tombstones, free/dock/display placement, automatic sizing/collapse/levels/freeRestore; all immutable days/notes/items/capture times/deletion/direct-carry labels; archives; settings and native preferences; rollover active-day/high-water; complete pending-deleted note/item membership. Schema metadata is regenerated from the validated schema version, not accepted as arbitrary SQL. Transient five-second deletion undo, text undo/selection/focus, OS login registration, temporary all-topmost mode and presentation-only rail selection are deliberately not durable backup state. Dates use Foundation Codable numeric seconds since2001; civil keys remain Gregorian strings.

Validation decodes a typed versioned envelope, rejects invalid/duplicate/orphan/carry/archive/checkpoint/settings/hotkey data, stages into isolated real SQLite, inserts snapshot children before sealing day headers, enforces FKs/integrity and re-exports through production decoding. Destination replacement refuses missing confirmation, marked composition and active transactions. SQLite `backup_init/step/finish` holds a destination transaction; incomplete copy finishes with rollback. No triggers are dropped and the shared Store connection survives. Export flushes owner edits in a transaction before snapshotting; thrown flush rolls back preceding writes. Native file export uses atomic Data write. These checks do not prove filesystem crash durability after power failure.

Integration order reviewed: imported hotkey candidate registers before DB replacement; any registration/import/persistence failure retires the candidate and keeps old binding. Successful replacement retires old binding, marks cards invalid before relinquishing focus, cancels menus/drag rails/reveal callbacks, clears native/shared undo, rebuilds controllers on the same store and reloads visible History. Same-ID import cannot republish stale editor content. No imported login intent calls register/unregister. Import itself does not rollover; subsequent scheduler/startup handles its checkpoint normally. Native runtime/focus/late-notification/animation acceptance remains required.

Public SDK signature review found **no reason to replace synchronous login APIs with speculative async work**: Apple's [register()](https://developer.apple.com/documentation/servicemanagement/smappservice/register()) and [unregister()](https://developer.apple.com/documentation/servicemanagement/smappservice/unregister()) document synchronous throwing methods. The separate [unregister(completionHandler:)](https://developer.apple.com/documentation/servicemanagement/smappservice/unregister(completionhandler:)) also has an async import; it does not invalidate the synchronous overload used here. `mainApp.status`, pending approval and explicit settings opening remain public API. [NSAccessibilityCustomAction](https://developer.apple.com/documentation/appkit/nsaccessibilitycustomaction) documents the name/Bool-handler initializer used in N10.

Actor assumptions: AppDelegate/presentation/controllers/services are main-actor bound, AppKit views/windows inherit UI isolation; synchronous Store operations never suspend/dispatch within transaction closures. Timer closures use `MainActor.assumeIsolated` only on timers installed on `RunLoop.main`; Carbon's noncapturing C callback uses an opaque retained-by-app owner and assumes application-target delivery on the main event loop. `GlobalHotkey.stop()` removes handler/registration before owner teardown. That **runtime delivery assumption and SDK-imported annotations remain native compile/runtime gates**, not something Linux parsing validates. Public ColorSync UUID ownership/CF bridge, AppKit field-editor delegate and Carbon parameter buffer/signature/key-code mapping must all compile against the chosen SDK. No private API/permission workaround was added.
